# 高可用与灾备架构

本说明覆盖控制平面的 HA 模式、角色切换、复制与健康探测策略，便于运维和 SRE 制定部署与演练方案。

## 设计目标
- 在单 AZ 内具备主备或主动-主动能力，最小化租约与配置的 RPO/RTO。
- 提供可观测的复制延迟与健康信号，便于外部负载均衡与前端 UI 判断。
- 支持手动或自动回切，并保留安全的隔离机制（fencing/抑制）。

## 组件与职责
- Failover 管理器（internal/failover）：
  - 角色管理：Primary/Secondary/Draining，持有心跳与健康状态。
  - 复制状态：记录延迟、最后同步时间、最近一次切换原因。
  - 回切控制：提供手动与自动回切入口。
- Server 层（internal/server）：
  - 读写路由：根据角色与延迟决定请求是否被接受或降级。
  - 健康探针：`/cluster/overview` 返回角色、延迟、抑制标记，供 LB 与前端使用。
- 数据层：
  - 数据库复制（外部）：MySQL 需配置主从或多主；应用侧通过只读/读写 DSN 分流。
  - 迁移控制：迁移仅在 Primary 执行，Secondary 拒绝迁移。

## 常见拓扑
- 主备（推荐）：一台 Primary，一台 Standby。LB 将写流量指向 Primary，读流量可按策略分配。
- 主动-主动（谨慎）：两台节点均可接收写入，依赖外部数据库的多主或冲突解决；应用层需要更严格的幂等与锁。
- 单节点（开发）：仅用于本地或 CI。

## 角色切换流程（示例）
1. 健康监测检测到 Primary 不可用或延迟超阈值。
2. 触发切换：标记 Primary 为 Draining，阻止新写入；Secondary 提升为 Primary。
3. 更新路由策略与连接池；刷新内存缓存。
4. 在恢复后进行回切（如启用自动回切，则等待稳定窗口）。

## 运维建议
- 探针与超时：
  - API 健康：`/cluster/overview` 结合 3xx/5xx 计数与延迟。
  - DB 健康：连接池错误率与复制延迟指标。
- 节点抑制：
  - 在维护窗口可将节点标记为 Draining，避免处理新请求。
  - 维护后执行健康检查再解除抑制。
- 日志与审计：切换事件应写入审计（internal/audit），便于追溯。

## 测试与演练
- 人工演练：
  - 人为暂停 Primary 的 DB 连接或进程，验证 Secondary 提升与 RTO。
  - 在租约/池写入负载下执行切换，验证幂等与冲突处理。
- 回滚演练：
  - 在 Secondary 提升后恢复 Primary，触发回切流程，确认无数据丢失。
- 指标校验：确保延迟、角色、抑制状态均可在监控与日志中观察到。
